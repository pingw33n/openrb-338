## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The m-1 engine renders an export offline. The UI needs it live: a real-time player that runs the engine in the audio callback of the chosen output library and takes commands from the UI thread without locks or allocation in the callback: transport (play, stop, locate, loop), pattern mode and song mode, every device parameter change (as the original applies them: docs/song_load.md, docs/export_state.md), pattern edits, mute, tempo, shuffle, the Vintage flag, loading a song and a mod; plus state the UI reads back (song position, the current step of each device, meter levels if the UI shows them). Output at 44.1 kHz (resample if the device does not offer it, and say how). The offline render (and so the corpus tests) must stay bit-identical; add a test that the player, fed the same song with no commands, produces the export's samples after the same idle count.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 A player crate or module plays a song through the chosen audio library with transport, pattern and song mode, and live parameter changes from another thread
- [x] #2 No locks or allocations happen in the audio callback (checked by a test or a debug allocator)
- [x] #3 A test shows the player's output equals the offline render for the same song and idle count

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Engine (no change to the offline output): make the process-global delay line lock-free (per-cell AtomicU32 and an AtomicBool gate instead of the Mutex), add SongDevice: Send, Devices::implemented_with(samples, ProcessState) so that a new song shares the old song's process globals, and Engine entry points for the live messages: set_param (slot 11, what the panel's knob messages do without record), the mixer master and channel enable (sub 145 id 0, sub 147 field 0), the msg 35 setters (song mode, loop, tempo, loop points, shuffle, Vintage id 21), playing(); readback: SongDevice::live() and ChannelDevice::playing_pattern().
2. New crate crates/rb-player (a crate, not a module of rb-cli: the m-3 UI crate and rb play both use it, and it carries cpal, rtrb, triple_buffer and rubato, which the offline render must not depend on). Player (UI side) and Audio (callback side): an rtrb SPSC command queue; a garbage queue that carries every box the callback lets go (old engines, data blocks) back to the UI thread to be dropped there; a triple_buffer snapshot (position, transport, mixer live values and meters, every device's live block, the playing patterns, the pending flag, faults). The engine renders 1024-frame calls (the original's MME buffer) into a FIFO that the callback drains; commands are applied before each engine call, as SafeSoundCallback drains the messages before it renders.
3. Song load: the UI thread builds Engine::new + load with the shared ProcessState and sends it; the callback activates it as msg 53 does: current song stopped -> slot 6 (the delay refill) and the swap; current song playing -> pending; Play on a pending song runs sub_1001BE74 (halt the old song, slot 6 on it, play the new one, swap). A mod is the sample set the new engine is built with.
4. Output: cpal's default device; 44.1 kHz when it offers it, else rubato's Async sinc resampler (FixedAsync::Input, 1024-frame chunks) to the device rate; f32 conversion i16/32768, any sample format through cpal's FromSample, extra channels zero.
5. Tests (driving Audio directly, no device): AC#3 player == offline export (and the corpus sha256) for the diag and app corpus songs after the same idle count; a counting global allocator test of the callback with every command kind, a song swap and resampling; transport, pattern, song mode and live parameter tests; the mixer ctor-track chase-back test of task-034.
6. rb play SONG subcommand in rb-cli for manual listening.
7. docs/export_state.md section 3: the switch facts ([G] -> [C] for when sub_1001C524 runs). Follow-up tasks for the live device messages (msg 41 subs), the mod change of an open song, and record.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
New crate crates/rb-player: the engine rendered in a cpal output callback, driven from the UI thread through lock-free, preallocated channels (rtrb command and garbage queues, a triple_buffer snapshot), with no lock and no allocation or free in the callback. The engine renders 1024-frame calls (the original's MME buffer) and applies the queued commands before each, as SafeSoundCallback does. Commands: play, stop, locate, song/pattern mode, loop on/start/end, tempo, shuffle, Vintage, any device controller (slot 11, which is what the panel's knob messages do with record off: 303 msg 40 read at 0x10025CFC), the mixer master and mute (msgs 145/147), a device data block, and song loads built off the audio thread, which the callback makes current as msg 53 does, including the pending-song switch when the current song plays (Play on the pending song runs sub_1001BE74; the other path, sub_1001C524, runs only on MIDI Start 0xFA: [G] -> [C] in docs/export_state.md section 3). Snapshot: position, transport, mixer live values and meters, every device's live block (with the playing step), playing patterns, pending flag, faults, output errors. Output at 44.1 kHz when the device offers it, else rubato's sinc resampler (an error there silences the rest of the callback and is counted); rb play SONG plays through the default device and exits on a stream error.

Engine changes, none to the output: the process-global delay line is atomics instead of a Mutex (the only lock on the render path), SongDevice: Send, Devices::implemented_with (songs share the process globals), live-message entry points and readback. Facts in docs/export_state.md section 3 and docs/song_load.md 3 and 4.10.

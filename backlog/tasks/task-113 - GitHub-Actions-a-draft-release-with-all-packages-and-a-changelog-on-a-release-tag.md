## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: the user asked (2026-10-28) that pushing a release tag makes GitHub Actions create a release with all the packages and a changelog. The release is saved as a draft so the user publishes it by hand.

The tag:
- Release tags are v + the version YYYY.MMDD.HHMM (the user's decision, 2026-10-28; task-133), e.g. v2026.1028.1930: the UTC date and time to the minute, the same form as the version in the binary and the package names (task-102's About box, '2026.1028.1930 (abc1234)'). Note in docs/building.md that the tag names the release moment and is chosen by the user; the packages' own build time is then the tag's (SOURCE_DATE_EPOCH from scripts/version.sh --epoch TAG).
- The workflow triggers only on tags that match this pattern, checked with a regex in a first job: tags: ['v*'] plus ^v[0-9]{4}\.[0-9]{4}\.[0-9]{4}$. Another tag fails with a clear message and creates nothing.

What:
- release.yml (task-108) gets a final job that runs after every package job (needs:):
  - It downloads all artifacts: the .tar.gz of every target (task-108), the .dmg (task-110), the two Windows installers (task-111) and the two AppImages (task-112).
  - It writes SHA256SUMS.txt over them.
  - It creates a draft GitHub release named after the tag, with every package and SHA256SUMS.txt attached.
  - Use the gh CLI with GITHUB_TOKEN (permissions: contents: write), or a pinned action such as softprops/action-gh-release, with draft: true. Never publish automatically.
  - Re-running for the same tag updates the existing draft (replaces the assets) instead of failing or making a second one.
- The changelog is the release body. It is generated from the commits between the previous release tag (the latest tag matching the pattern before this one, by version order) and this tag:
  - group the commit subjects by their area prefix (engine:, cli:, tools:, tests:, docs:);
  - leave out backlog: commits;
  - list the task ids from each commit's Task: trailer;
  - for the first release, take all of history, or a configurable start, and say which.
  - Write the generator as a small script in scripts/ (shell or Python, no extra dependencies). The workflow calls it, and it runs locally (scripts/changelog.sh vPREV vNEW), so the user can preview it.
- Document in docs/building.md how to cut a release: the tag command, what the workflow produces, and how to publish the draft.
- Validate: actionlint on the workflow, and a local run of the changelog script over this repository's history between two test tags. Don't push tags to origin. If act can run the release job against a local tag without publishing, record it.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Addition from the user (2026-10-28): every binary of a release has the same build time, the tag's. A first job parses the tag (v-YYYY_MM_DD_HH_MM_SS, UTC) into a Unix time and passes it to every build job as SOURCE_DATE_EPOCH (job outputs, then env), which task-102's build script uses for the version string. The same job sets RB_BUILD_BRANCH=main when the tagged commit is on main (git merge-base --is-ancestor with origin/main, after a full fetch), else the tag's branch is not main and RB_BUILD_BRANCH is left unset (so the version shows dev-). Check: the version strings printed by the built binaries (e.g. rb-ui --version or an equivalent the build exposes; add a --version flag to rb-ui if there is none) are identical across all packages and equal the tag's time, e.g. tag v-2026_10_28_10_10_22 -> '2026-10-28 10:10:22 (7bd8876)'. Record it in docs/building.md.

From task-110 (user decision 2026-10-28): the version of every package is the UTC build time, never the Cargo version (0.1.0).
